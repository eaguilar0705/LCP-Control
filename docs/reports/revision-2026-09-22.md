## 2. Flujo correcto de confirmación por correo

1. `/activate` → `signUpStaff(email, password)` con `options.emailRedirectTo = <origen>/auth/callback`.
2. El disparador `provision_lcp_staff` crea la fila de `staff_members` desde `private.pending_staff` (sin cambios).
3. La persona abre el enlace → Supabase `/auth/v1/verify` confirma el correo y redirige a `/auth/callback#access_token=…&refresh_token=…&type=signup` (o `#error_code=otp_expired`).
4. `AuthCallbackPage` lee el enlace una sola vez (a prueba de StrictMode), reemplaza la URL por `/auth/callback`, llama a `confirmAuthLink` (`setSession` / `verifyOtp` / `exchangeCodeForSession`).
5. `onAuthStateChange` publica la sesión; `AuthProvider` carga el rol y la pantalla navega a `/` (o `/account` para recuperación).

Configuración pendiente en Supabase (no se puede hacer desde el código): Site URL con el dominio HTTPS definitivo, `https://<dominio>/auth/callback` en *Redirect URLs* y SMTP propio. Detalle en [database.md](../guides/database.md#enlaces-de-correo-activación-cambio-de-correo).

## 3. Migración de base de datos

`supabase/migrations/20260923120000_contact_deletion.sql` — **no destructiva**: sólo crea `private.contact_deletions` (bitácora privada) y dos funciones.

- `delete_customer(p_id, p_revision)`: sólo Administrador. Si el cliente tiene facturas o proformas se **archiva** (`active = false`) para no romper `documents.customer_id`; si no, se elimina. Devuelve `'archived'` o `'deleted'`.
- `delete_supplier(p_id, p_revision)`: sólo Administrador. Los proveedores no tienen claves foráneas (las compras guardan el nombre), así que se eliminan.
- Ambas comprueban la revisión (no borran algo que otra persona acaba de cambiar), comparten el candado de `save_customer`/`save_supplier` y el límite de escrituras.
- Pruebas: `tests/database/contacts.mjs` (permisos, revisión, archivado con documentos, bitácora privada).

Aplicar con `supabase db push` o pegando el archivo en el editor SQL. Hasta aplicarla, el botón «Eliminar» responde con un error de función inexistente; editar funciona sin la migración.

## 5. Auditoría de botones y listas desplegables

Se revisaron **113 botones** (`<Button>`/`<button>`) y **35 listas** (`<Select>`/`<select>`) en 26 archivos con un analizador de JSX y lectura manual. Criterios: manejador asignado (o `type="submit"` dentro de un formulario), `type` explícito, estado de carga en acciones asíncronas, deshabilitados justificados, sin manejadores vacíos.

Resultado general: **ningún manejador vacío ni «dummy»**; ningún botón con `onClick` dentro de un formulario sin `type="button"` (no hay envíos accidentales). Los hallazgos y correcciones:

| Componente | Estado encontrado | Corrección |
| --- | --- | --- |
| Login · campo Contraseña | Sin forma de ver lo escrito. | `PasswordInput` con botón mostrar/ocultar (`aria-pressed`, no envía el formulario, oculta el ojo nativo de Edge). |
| Activar cuenta · «Crear mi acceso» | Envío implícito, sin distinguir cuenta existente. | `type="submit"`, `aria-busy`, detección de cuenta confirmada, contraseña con mostrar/ocultar. |
